# 2026.11.27-1 · 原生客户端登录恢复与本机解锁

> **Release 版本号**：[`2026.11.27-1`](https://github.com/YouZiFeiLe/Chirp/releases/tag/2026.11.27-1)（已发布 · 2026-11-27）
> **涉及平台**：Go 服务端 · Apple（macOS / iOS）· Android · Windows
> **核心主题**：在不让业务 Bearer 落盘的前提下，实现基于系统本机验证与 V5 设备私钥签名的冷启动登录恢复

iOS、macOS、Android 和 Windows 现在共用一套设备绑定的登录恢复协议。第一次通过 Passkey 并完成设备激活后，服务端返回的业务凭证 `expires_at` 是**在线使用与本地恢复的共同绝对截止时间**——取凭证签发后 **20 小时**与设备叶证书到期时间的较早者。无论是锁屏切回、应用重启还是重复恢复，都严格沿用这同一个截止时间（例如登录后 19 小时 59 分重开应用，若设备证书仍有效，通过本机验证即可恢复，剩余有效时间约 1 分钟；到期后则必须重新走 Passkey 认证）。[业务凭证签发源码](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/store/client_login.go)

## 一、设计方案：为什么变更，用户能获得什么

此前版本的原生客户端仅将业务 Bearer 凭证保存在进程内存中：用户刚完成 Passkey 登录，一旦被系统后台回收进程、在最近任务划掉或主动关闭应用，重新打开时仍必须再次跳转浏览器或使用手机扫码授权。若为本地恢复单独设立更长的有效期，又会导致同一账号在同一时刻因为进程是否被系统回收而产生不一致的权限结果。

新方案在保留「业务 Bearer 绝不落盘」与「共同 20 小时上限」的前提下，将**冷启动恢复能力**下沉到操作系统的逐次认证安全存储与服务端挑战-响应机制中：

| 使用场景 | 用户体验与处理结果 |
| --- | --- |
| **首次登录 / 原业务凭证到期** | 仍通过 Passkey 授权并验证设备，获得全新登录代次与截止时间。 |
| **切后台、锁屏后返回（原进程仍在）** | **不重复弹窗**：直接沿用进程内存中的登录会话和通话；客户端核对到期时间并继续接收服务端状态推送。 |
| **划掉任务、关闭应用或进程被系统回收后重开** | 若存在未过期的受保护恢复记录，新进程首次进入前台时自动唤起系统本机验证（Face ID / Touch ID / 强生物识别 / Windows Hello）；验证通过后用原设备私钥签名联网换取新 Bearer（进入房间仍须重新完成入房与配钥流程）。 |
| **首次登录时服务端未签发恢复凭证，或系统无法安全保存** | 当前进程内可照常使用；进程结束后需要重新 Passkey 登录。具备恢复条件后再完成一次 Passkey 登录即可启用冷启动恢复。 |
| **取消本机验证或暂时断网** | 界面保持锁定状态；用户可在原截止时间内点击重试解锁，或随时改用 Passkey 重新登录。 |
| **主动退出登录** | 立即彻底清除本机恢复材料；若当前持有效在线 Bearer，则同步向服务端注销。下一次打开必须重新 Passkey 登录。 |
| **其他设备接管、账号停用或设备撤销** | 服务端会在发挑战与验签阶段拒绝旧登录，客户端收到确定失效错误码后自动清理本地恢复记录。 |

## 二、服务端接口、存储与签名实现原理

### 1. 服务端接口与事务模型

新增的三个处理链路均向已核验的 `passkey_origin` 发送 JSON `POST` 请求，继续携带 `X-Chirp-Platform`（`ios`、`macos`、`android` 或 `windows`）、`X-Chirp-Version` 与 `X-Chirp-Build` 请求头。注意部分部署中业务 API 地址与身份认证服务 `passkey_origin` 可能不同。[HTTP 处理器](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/passkeyhttp/identity_setup.go) · [客户端头校验](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/clienthttp/version.go)

| 接口路径 | 请求内容与能力声明 | 成功响应与服务端原子处理 |
| --- | --- | --- |
| `POST /api/client/identity/complete` | 沿用原有 Passkey + PKCE 设备激活请求；支持安全恢复的客户端附加请求头 `X-Chirp-Login-Resumption: 1` | 在原登录响应（`credential`、`expires_at`、`member`、`participant_identity`、`device_identity`）基础上，启用恢复时附加 `resume_token`。旧服务端不返回此字段时，本次内存登录依然可用。 |
| `POST /api/client/resume/challenge` | `{"resume_token":"<恢复凭证>"}` | 返回 `{"challenge":"<随机挑战>"}`。挑战最长有效 **1 分钟**，且受原业务 `expires_at` 截止时间封顶；同一尚未消费的挑战在有效期内可重复取得。 |
| `POST /api/client/resume/complete` | `{"resume_token":"<恢复凭证>","signature":"<设备签名>"}` | 返回**同一登录代次**、**原 `expires_at`** 与**新 `credential`**。客户端核对账号、参与者及完整设备身份一致后解锁。原 Bearer 即刻失效，恢复凭证在原期限内可继续用于后续冷启动。 |

- **持久化表结构与平滑升级**：服务端在主库新增 `client_login_resumptions` 表（`member_id` 主键外键级联删除、32 字节 `token_hash` 唯一索引、绑定 `login_id`、`origin`、`platform`、`challenge` 与 `challenge_expires_at`）。该表在数据库初始化前置阶段通过 `CREATE TABLE IF NOT EXISTS` 创建，**继续沿用 SQLite Schema `23`**，存量部署升级镜像即可无缝兼容。[建表 SQL](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/store/schema.sql)
- **并发与防重放事务**：服务端按 `resume_token` 的 SHA-256 摘要查找记录，严格匹配平台、规范 `origin`、账号和当前 `login_id`；在签发挑战与验证签名两处分别复核凭证期限、客户端版本策略、账号启用状态、设备证书链及黑名单。验签成功时，**单个写事务内同时消费挑战并轮换 Bearer 摘要**，保留原有 `login_id` 与入房序列；并发提交同一证明只有一次能成功，若响应在网络上丢失，客户端可重新请求新挑战并再次签名。[恢复事务源码](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/store/client_resumption.go)

### 2. 规范消息编码与跨端测试向量

恢复证明使用独立签名域标签 `Chirp login resumption v1`，由原 V5 设备的 Ed25519 叶私钥对以下 **7 个字段**顺序拼接后的字节流签名。每个字段（包括域标签）均先写入 **4 字节大端无符号 UTF-8 字节长度**，再紧接字段原文；Ed25519 签名采用带填充的标准 Base64 传输。[规范字节定义](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/identity/protocol.go) · [恢复消息构建](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/identity/activation.go)

| 顺序 | 字段内容 |
| --- | --- |
| 1 | 字面值 `Chirp login resumption v1` |
| 2 | 规范化身份服务 origin，含 scheme、规范主机与显式端口（例如 `https://keys.example.test:443`） |
| 3 | 请求的实际平台名（`ios` / `macos` / `android` / `windows`） |
| 4 | 首次登录响应中的完整 `participant_identity`（格式 `member_id.login_id`） |
| 5 | 对完整 `resume_token` 的 UTF-8 字节计算 SHA-256 后取标准 Base64 文本（令牌前缀参与哈希） |
| 6 | 服务端返回的 `challenge` 原文（32 字节随机数编码为无填充 Base64URL 文本） |
| 7 | V5 设备身份摘要，即 `Device.Hash()` 的标准 Base64 文本（覆盖整条设备证书链） |

**跨端校验样例**（采用仓库 V5 向量的 `device`、上述 origin 样例、平台 `android` 及参与者 `member_fixture.login_fixture`；公开测试向量可用于联调比对 Base64 变体、字段顺序与长度前缀）：[V5 设备向量](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/identity/testdata/v5.json) · [Go 对照测试](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/identity/vectors_test.go)

```text
resume_token       resume-v1_AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8
challenge          ICEiIyQlJicoKSorLC0uLzAxMjM0NTY3ODk6Ozw9Pj8
device_digest      B2OupV0g1omfnvJm4I8JfohQCvn7yAv+8P/cfItvL4E=
token_sha256_b64   bFSEn41asLYKn+esux2icvSTGymvnfv4xXqjZU5Nhe0=
message_sha256_b64 nOrZz5uNpOPV7sgnW/wGZ26KFdcd0z3Z4+6I2reXpr8=
```

新接入端统一使用带版本前缀的 `resume-v1_` 恢复凭证。服务端与 Apple 客户端同时对早期签发的 `resume_` 兼容过渡：升级时会保留尚在有效期内的记录、作废待签挑战，已过期记录不会复活。

## 三、安全性如何变化

与纯内存登录相比，本机新增了一份可用于申请恢复新 Bearer 的长期凭证（`resume_token`），但**业务 Bearer 本身依然仅存在于进程内存中**：

1. **防凭证窃取与跨机重放**：单纯复制恢复凭证、复制普通应用偏好设置，或截获某一次已提交的签名，均无法在另一台设备取得业务权限——服务端强制要求持有当前设备的 V5 私钥针对当次单次挑战完成签名；且注销、换机接管、设备吊销与原始 20 小时到期在恢复时照常拦截。[恢复校验与拒绝路径测试](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/store/client_resumption_test.go)
2. **本机用户验证与存储隔离**：生物识别或设备密码校验由操作系统本地完成，服务端仅验证设备签名，不会收到人脸、指纹或系统密码。所有平台均将恢复秘密的读取或解封直接绑定到本次系统认证（`LAContext` / `BiometricPrompt.CryptoObject` / Microsoft Passport `NCryptDecrypt`），普通配置仅保存唤起锁定界面所需的非秘密到期提示。
3. **热切与锁屏边界**：普通切换应用或息屏切回依赖设备本身的锁屏保护，运行中进程的合法会话将继续保留；服务端撤销检查、原始到期时间与移动端最近任务预览遮挡同步生效。

## 四、四端客户端实现细节

### 1. Apple（macOS & iOS）

- **逐次认证钥匙串**：使用 Data Protection Keychain（`kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` 且关闭 iCloud 同步）。iOS 通过 [`biometryCurrentSet`](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/biometrycurrentset) 将读取绑定到当前登记的生物识别集（Face ID / Touch ID），macOS 使用 `userPresence`（支持 Touch ID 或系统账户密码）。每次冷启动解锁创建全新的 `LAContext`。[Apple 恢复记录存储](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/apple/Shared/SavedLogin.swift)
- **原子索引与生命周期**：在登录确认前即将随机生成的钥匙串条目名与到期提示原子写入排除备份的应用目录，确保即使用户登录后立刻划掉应用，下次启动也能找到记录（同时兼容读取旧版偏好设置索引）。`ChirpApp.swift` 与 `LoginSession.swift` 联合监听窗口前后台状态：仅新进程首个前台窗口就绪时自动发起一次验证，取消或切后台中断后保持锁定页（`LoginLockView.swift`），由用户手动点击重试；已在登录态的进程切回前台仅校验到期时间，不打扰通话。[Apple 生命周期](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/apple/Shared/ChirpApp.swift) · [解锁状态机](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/apple/Shared/LoginSession.swift) · [锁定界面](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/apple/Shared/Views/LoginLockView.swift)

### 2. Android

- **Android Keystore + `CryptoObject` 逐次加密**：激活完成时使用随机 AES-GCM 密钥加密恢复记录，再以 Android Keystore 专用 RSA 公钥封装该 AES 密钥，并将到期提示与密文原子写入 `noBackupFilesDir/login-resumption-v1`。冷启动恢复时，通过 [`BiometricPrompt.CryptoObject`](https://developer.android.com/reference/kotlin/android/hardware/biometrics/BiometricPrompt.CryptoObject) 将 RSA 解封操作严格绑定到本次强生物识别认证（`BIOMETRIC_STRONG`）；重新登记或增删指纹会使硬件私钥永久失效。[受保护的记录库](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/android/app/src/main/kotlin/cn/youzifeile/chirp/data/BiometricLoginVault.kt) · [恢复协议实现](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/android/app/src/main/kotlin/cn/youzifeile/chirp/data/LoginResumption.kt)
- **任务释放与预览遮挡**：从最近任务划掉应用依然会立即销毁通话与内存 Bearer；若恢复记录有效，重开后呈现 `LockedLoginScreen` 并自动发起一次指纹/面部解锁。同时新增 `TaskPreview.kt` 对账号页及关键对话框进行最近任务截图遮挡。[任务释放](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/android/app/src/main/kotlin/cn/youzifeile/chirp/ChirpApplication.kt) · [最近任务遮挡](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/android/app/src/main/kotlin/cn/youzifeile/chirp/TaskPreview.kt)

### 3. Windows

- **按需启用 Windows Hello 与双层密封**：首次登录仍直接打开 Passkey 网页，用户可在登录后的通用设置中主动开启 Windows Hello。支持 Hello 的客户端在设备激活时申请 `resume_token`，在用户启用前仅保存在 Go 引擎内存。WinUI 使用 Microsoft Passport Key Storage Provider 创建要求每次使用私钥都验证用户的本机 RSA 解密密钥，并重新打开密钥核对保护策略；随后用真实密文与输出缓冲区调用 [`NCryptDecrypt`](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/nf-ncrypt-ncryptdecrypt)，**仅当提供程序明确拒绝静默解密时**，才由 Go 引擎使用随机 AES-256-GCM 密钥加密记录、用 Hello 公钥封装数据密钥并原子写入本机缓存目录（已有密钥的电脑在后续登录可静默读取公钥直接落盘）。[Windows Hello 密钥](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/windows/Chirp/WindowsHelloLoginKey.cs) · [Windows 恢复引擎](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/windows/engine/resumption_windows.go)
- **多窗口共享锁定与静态预览**：新进程所有窗口共享同一 `LoginLock` 状态；首个前台窗口在网络时间校验通过后自动请求一次 Windows Hello，取消、最小化、切应用或锁屏会中断正在进行的解锁，保留锁定页供手动重试。任务栏与任务切换器显示静态安全预览。关闭所有窗口保留有效恢复记录，而点击设置中的「退出登录」会彻底清除本地记录并向服务端注销。[前台解锁](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/windows/Chirp/LoginResumption.cs) · [窗口与预览](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/windows/Chirp/MainWindow.xaml.cs)

### 4. 四端统一错误映射、诊断事件与附带改动

- **新增标准错误码**：在 [`ClientError.swift`](https://github.com/YouZiFeiLe/Chirp/blob/main/Client/apple/Shared/ClientError.swift) 与双语 `Errors.strings` 中新增 `CLIENT_LOCAL_UNLOCK_FAILED` 与 `RESUMPTION_PROOF_INVALID`；服务端 [`server.go`](https://github.com/YouZiFeiLe/Chirp/blob/main/internal/passkeyhttp/server.go) 对 `store.ErrResumptionProof` 返回 `409 RESUMPTION_PROOF_INVALID`（允许重取挑战重试），而 `INVALID_AUTHORIZATION`、`MEMBER_DISABLED`、`IDENTITY_BLACKLISTED` 等确定失效响应则会清除本地记录并退回登录页。Windows 引擎另区分本机存储与 Hello 密钥不可用状态（`LOGIN_STORAGE_UNAVAILABLE`、`HELLO_KEY_UNAVAILABLE`）。
- **新增 `.chirplog` 诊断事件**：若已开启本地日志，可通过 `account` 表中的 `loginWithoutResumptionGrant`（服务端未签发恢复凭证或本机不可用）与 `saveLoginForRelaunch`（本地密封保存状态）排查冷启动恢复未生效的原因；Windows 引擎另记录 `resumeLogin` 与 `unlockLogin` 命令耗时。
- **附带界面与仓库入口优化**：同步在 Apple「设置 / 关于」、Android「关于 Chirp」、Windows「通用设置」以及网页端 `/register`、`/device`、`/admin/` 增加了 Chirp GitHub 开源仓库入口，并更新仓库 GitHub Social Preview 图片。
